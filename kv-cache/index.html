The KV cache

Why language models remember the keys and values of every token they've seen, how much work that saves, and why it ends up being one of the biggest memory costs in LLM serving.

1 Models write one token at a time

A language model is autoregressive: to write a sentence it predicts one token, appends it to the input, and runs again to predict the next one. Every new token needs the model to "look at" every token before it.

The naive way to do that is to feed the entire sequence back through the model at each step. That means the 1000th token pays for re-processing the 999 before it — work that was already done on the previous step. The KV cache is the trick that stops this.

Key idea. In a decoder-only transformer, a token's keys and values never change once computed, because of the causal mask (a token can only see tokens before it). So compute them once, store them, and reuse them forever.

2 A 60-second attention refresher

Each token's hidden vector x is projected three ways by learned matrices:

Q query = x·WQ — "what am I looking for?"
K key = x·WK — "what do I contain?"
V value = x·WV — "what do I hand over if picked?"

A token's output is a weighted average of the values of all tokens up to and including itself, with weights softmax(q · kᵢ / √d). Only the current token's query is used, but the keys and values of every earlier token are needed. That asymmetry is the whole story.

4 Only the last row is new

Here's the full causal attention matrix: row i is token i's query, column j is token j's key. At each decode step, without a cache the model recomputes the whole lower triangle. But the rows above the new one are outputs for old positions — they were already used to predict earlier tokens and nobody needs them again. The new row needs only one new query and all the keys (the columns). So: cache K and V, never Q.

5 How much work does it save?

Without a cache, step t recomputes K and V for all t tokens and the full t × t triangle of attention scores. With a cache, step t computes K and V for one token and one row of t scores. Summed over a whole generation, quadratic becomes linear (and cubic becomes quadratic).

The catch. Nothing is free: the cache turns a compute problem into a memory problem. Each decode step has to read the model weights plus the entire KV cache from GPU memory to do very little arithmetic, so decoding is usually limited by memory bandwidth, not FLOPs. And the cache itself has to live somewhere…

7 Shrinking the cache: MHA → GQA → MQA

The cache scales with the number of KV heads, not query heads. Classic multi-head attention (MHA) gives each query head its own K/V head. Grouped-query attention (GQA) lets a group of query heads share one K/V head, and multi-query attention (MQA) shares a single K/V head across all of them. Fewer KV heads → proportionally smaller cache, usually with little quality loss.

8 Serving many users: paging the cache

A server doesn't know in advance how long each reply will be. The simple approach reserves a contiguous slab for the maximum length per request, so most of it sits empty. PagedAttention (vLLM) borrows the idea of virtual memory: split the cache into small fixed-size blocks and hand them out on demand, anywhere in memory. Less waste → more requests in flight → higher throughput.

9 Check yourself

Going further

Prefix caching

Requests sharing a system prompt can share its KV blocks instead of each recomputing them.

KV quantization

Storing K/V in 8 or 4 bits halves or quarters the cache, at a small accuracy cost.

Sliding-window attention

Only attend to the last W tokens, so the cache stops growing past W per layer.

Multi-head latent attention

Cache a small compressed latent per token and reconstruct K/V from it (DeepSeek-V2 and later).

Eviction

Drop the least-attended tokens (e.g. keep "attention sinks" plus recent tokens) to bound memory.

Offloading

Spill cold parts of the cache to CPU memory or disk and fetch them back when needed.
